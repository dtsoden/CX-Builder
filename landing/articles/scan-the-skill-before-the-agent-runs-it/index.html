Agent security • Field note

Check every add-on before your support agent can run it

NVIDIA just released a free scanner for AI agent skills. The tool is useful, but the habit behind it matters more: nothing gets plugged into an agent that talks to your customers until someone has looked at it.

David Soden • 5 min read • 16 November 2026 Share on LinkedIn

What happened

NVIDIA has released SkillSpector, an open-source scanner for AI agent skills. A skill is a packaged set of instructions that teaches an agent a new task. Many are just written guidance, but some ship with small scripts that can run commands, read the environment variables where passwords and API keys often live, and reach into the folders that hold server login keys.

You point SkillSpector at a skill and it tells you whether to install it. It looks for code that runs arbitrary commands, follows secrets to see whether they get sent anywhere, checks for known malware signatures, and flags hidden instructions meant to hijack the agent, including text disguised with invisible characters. It checks the skill's dependencies against a public database of known vulnerabilities. An optional second pass uses a language model to weed out false alarms. The result is a risk score, a list of findings, and a plain "do not install" when a skill with executable code turns up several serious problems. It's free on GitHub.

The Help Net Security write-up cites research finding that skills which ship with scripts are about twice as likely to be vulnerable as those that don't. That fits what you'd expect. Instructions can mislead an agent, but code can act.

Why this matters to your business

An add-on gets whatever access the agent has. If your support agent can read customer records, issue refunds or update accounts, so can every skill, tool and connector you attach to it. Installing one from an unknown source is closer to hiring a contractor and handing over the building keys on day one than it is to installing an app.

Most companies have a vendor review process for new software. Agent add-ons tend to skip it, because adding one doesn't look like buying software. A developer copies a folder or pastes a configuration, and the agent can do something new by the afternoon. Nobody in procurement or security ever sees it.

The failure cases are concrete. An API key leaks to a server you've never heard of. Customer data leaves through a tool that was supposed to format addresses. A hidden line in an instruction file tells the agent to skip a policy check. Any one of these can end in a breach notification, and in a support setting the customer often finds out before you do.

Why this is a CX-Builder use case

CX-Builder doesn't scan skills, and it doesn't need to for this to work. What it gives you is a place where every capability an agent has is visible and was added on purpose. Tools, connectors and MCP servers show up as nodes in the flow. If a support agent can issue a refund, there is a refund tool on the canvas, and someone put it there.

That visibility makes a review step practical. Because CX-Builder is self-hosted, nothing reaches your agents unless your team installs it. Credentials live in one credential store and are assigned to individual nodes, so a lookup tool can get a read-only key while the refund tool gets a different one. Tools that change something can be set to wait for human approval before they run, so a bad add-on that slips through still can't act on its own. And a flow imported from a template or a colleague arrives as something you can open and read before any customer touches it.

What this looks like if you build it

Treat third-party tool code, skills and MCP server configurations like any other code your company ships. Keep them in a repository and run a scanner in the pipeline before anything is added to a flow. SkillSpector covers the skill format and writes SARIF, which most CI systems can read, and your existing dependency and code scanning can cover custom tools. In the agentflow, give each tool its own narrow credential, switch on Require Human Input for any tool that writes or refunds, and test new tools in a staging flow before they go near production traffic.

None of that is exotic. It's the review your company already does for new software, applied to the thing that has started to behave like software.

The takeaway

This quarter, list every skill, tool and connector your customer-facing agents can call, along with who added it and which credential it holds. Anything nobody can vouch for comes out until someone has read it. Then make the scan and the approval a required step, so the list stays clean without anyone having to remember.
